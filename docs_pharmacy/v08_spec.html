SECTION 2テーマ／レイアウト切替

2.1 テーマ（配色）

  • html[data-theme="day"|"night"] で切替。CSS変数はすべて意味名（--bg --surface --ink --ink-sub --act --warn --danger --line）。値は企画書§07のトークン表に従う。
  • 判定順序：① localStorage p8_theme が day|night なら常にそれ ② auto（既定）なら JSTの時刻で 20:00–5:59 = night、それ以外 day。
  • 手動切替UI：ヘッダー右端のボタン（🌙/☀️）。タップで day→night→auto の3状態巡回。auto時はラベルに「自動」と現在の判定結果を併記。
  • 自動切替の再判定は setInterval 60秒ごと。切替時は transition: background-color .2s, color .2s（bodyと主要面のみ。全要素 * への transition 指定は禁止＝再描画コスト）。
  • prefers-reduced-motion: reduce 時は全 transition/animation を 0s に（app.css 末尾で一括上書き）。

2.2 レイアウト（画面構成）

  • テーマとは独立に画面幅で決定：<768px=モバイル（ボトム4タブ：出庫・在庫・履歴・管理）／≥768px=デスクトップ（左サイドバー8項目）。CSSメディアクエリで同一DOMを出し分ける。
  • モバイルの「管理」タブはメニューリスト（今日の状態・入荷・発注・棚卸・マスタ整備・分析・テーマ切替）。
  • 初期画面：モバイル=出庫、デスクトップ=今日の状態。
  • サイドバーのバッジ：在庫切れ＋発注点割れ＋切迫（v_reorder集計）→発注、原価未設定数（v_master_gaps）→マスタ整備、要対応合計→今日の状態。数値はマスタ読込後に1回計算。

-- master_gap_exempt / stock_tracking を末尾列として追加（既存列の並び・名前は不変）

create or replace view pharmacy_v_master_gap_stats as
select count(*)::int as total,
       count(*) filter (where rezept_code  is not null or master_gap_exempt)::int as ok_rezept,
       count(*) filter (where cost_per_pack is not null or master_gap_exempt)::int as ok_cost,
       count(*) filter (where pack_size    is not null or master_gap_exempt)::int as ok_pack,
       count(*) filter (where price        is not null or master_gap_exempt)::int as ok_price
from pharmacy_medicines where active;

3.3 関数（RPC）3本

① コード採番 pharmacy_next_code()

create or replace function pharmacy_next_code() returns text
language plpgsql as $$
declare n int;
begin
  perform pg_advisory_xact_lock(hashtext('pharmacy_next_code'));
  select coalesce(max((regexp_match(code,'^M(\d+)$'))[1]::int),0)+1 into n
    from pharmacy_medicines where code ~ '^M\d+$';
  return 'M' || lpad(n::text, 3, '0');
end $$;
grant execute on function pharmacy_next_code() to anon, authenticated;

呼び出しは POST /rest/v1/rpc/pharmacy_next_code。採番→INSERTの間に他端末が同番号を取る可能性は残るが、PK衝突でINSERTが弾かれるため二重登録にはならない（失敗時は再採番してリトライ1回）。

② 棚卸の一括反映 pharmacy_apply_stocktake(...)

create or replace function pharmacy_apply_stocktake(
  _taken_on date, _operator text, _rows jsonb   -- [{code, counted, note}]
) returns jsonb language plpgsql as $$
declare r record; _sys int; _applied int := 0; _diff int;
begin
  for r in select * from jsonb_to_recordset(_rows) as x(code text, counted int, note text) loop
    select current_stock into _sys from pharmacy_medicines where code = r.code for update;
    if not found then continue; end if;
    insert into pharmacy_stocktakes (taken_on, medicine_code, system_qty, counted_qty, operator, note)
      values (_taken_on, r.code, _sys, r.counted, _operator, r.note);
    _diff := r.counted - _sys;
    if _diff <> 0 then
      insert into pharmacy_transactions (medicine_code, transaction_type, quantity,
        note, operator, occurred_on, source)
        values (r.code, 'adjust', r.counted,
                '棚卸' || coalesce('・'||nullif(r.note,''),''), _operator, _taken_on, 'app');
      update pharmacy_medicines set current_stock = r.counted, last_updated = now()
        where code = r.code;
    end if;
    _applied := _applied + 1;
  end loop;
  return jsonb_build_object('applied', _applied);
end $$;
grant execute on function pharmacy_apply_stocktake(date,text,jsonb) to anon, authenticated;

adjust の quantity には「新しい在庫数（絶対値）」を入れる＝v0.7の stockAdjust と同じ意味論。全行が1トランザクションで確定し、途中失敗時は全ロールバック。

③ 発注書の受入 pharmacy_receive_order(...)

create or replace function pharmacy_receive_order(
  _order_id bigint, _received_on date, _operator text,
  _rows jsonb   -- [{item_id, qty, expiry_on, lot_no}]  qty=今回受入する単位数
) returns jsonb language plpgsql as $$
-- 各行: pharmacy_lots へ INSERT（unit_cost は order_items.unit_cost/pack_size から換算、
--        expiry_on/lot_no は引数値）→ in トランザクション INSERT（lot_id 紐付け）
--        → pharmacy_medicines.current_stock 加算 → order_items.received_qty 加算
-- 最後に: 全 items で received_qty >= qty なら orders.status='received'、
--          1件でも受入があれば 'partial'、を判定して更新
-- 戻り値: {received_items: n, order_status: '...'}
$$;

本文はOpusが②と同じ流儀で実装（for update・1トランザクション）。pharmacy_orders.status の取りうる値に partial を追加する（text列のため制約変更不要。画面表示名=「一部受入」）。

5.2 状態・動作

  • QR自動起動：画面表示時に startScanner() を自動実行。失敗（権限拒否等）時は fallback 表示。カメラは他画面へ移動したら stop()（電池対策）。
  • スキャン成功：batchItems へ追加（同一薬の再スキャンは数量+1に集約。v0.7の別行追加をやめる）。行が上から160msで挿入され、行内に「在庫 162包 → 160包」を即時表示。振動1回。
  • 在庫不足（数量>現在庫・在庫管理対象のみ）：行を琥珀枠にし、確定時の確認モーダルに不足一覧を出す（v0.7のconfirm文言を流用・モーダル化）。
  • 出庫で発注点を割る薬：.low-warns に「⚠ ○○は残り15包（発注点180）」を1回フェードインで追加。消費ペースで数日内に切れる薬（v_reorder相当の簡易判定）も同様。
  • 担当者：localStorage p8_operator に保存し次回自動選択。担当者リストはv0.7の10名を定数移植（要確認事項③）。
  • 患者：フリーテキストのみ。過去に自分が入力した患者名を localStorage p8_recent_patients（最大20件）から datalist 候補に出す。重要v0_7の patientData ハードコード配列は移植しない。DBからの患者一覧取得も行わない。
  • 長押し確定 → 書き込みシーケンス（v0.7の doSubmitAll を整理移植）：
    ① pharmacy_transactions へ一括INSERT（operator列・occurred_on列を正式使用。note="担当:"の埋め込みは廃止し operator 列へ）
    ② 在庫管理対象のみ pharmacy_medicines.current_stock をPATCH
    ③ GAS recordPrescription（§13・fire-and-forget）
    ①が失敗したらオフラインキューへ（②③もキュー内に保持し再送時に同順で実行）。
  • 完了：ボタンがチェック表示（800ms）→リスト/患者クリア。担当者は保持。

5.4 受け入れ条件

  1. 画面を開いて3秒以内にQRスキャナが起動している（カメラ許可済み端末）。
  2. QR読取→数量調整→長押し0.6秒、の3操作で出庫が完了し、Supabaseの transactions に operator・occurred_on 入りの行が増え、medicines.current_stock が減っている。
  3. 同じQRを2回読むと行が2本にならず数量が2になる。
  4. 外用薬（stock_untracked=true）を出庫しても current_stock が変わらず、transactions には記録される。
  5. 長押しを0.3秒で離すと送信されない。
  6. 機内モードで確定→トーストと琥珀バー表示→通信復帰で自動再送され、二重送信になっていない（transactions件数で確認）。
  7. 出庫の結果 threshold を下回った薬の警告行が表示される。
  8. 21時台の初回アクセスで夜間配色、11時台で日中配色になる。手動で☀️に切り替えた状態はリロード後も保持される。

8.1 DOM構成・動作

#scr-stocktake
├── .st-head    … 棚卸日(date・既定=今日) / 担当者(select) / 進捗 n/88・進捗バー
├── .st-table   … 行=在庫管理対象の全品目（stock_untracked除外・分類→コード順）
│     列: 薬品名 / システム在庫 / 実地数(input) / 差分(自動) / メモ(input)
└── .st-foot    … 差分サマリ ／ [下書き保存] [差分を確認して反映]
  • 実地数input：Enter/Tabで次行の実地数へフォーカス移動（表を上から流し込める）。数値のみ・空=未入力。
  • 差分セル：入力の都度 counted - system を計算。0=ティール「±0」、非0=琥珀「＋n/−n」＋行ハイライト＋600msパルス1回。
  • 下書き：localStorage p8_stocktake_draft = {taken_on, operator, rows:{code:{counted,note}}}。画面を開いた際、同日付の下書きがあれば復元を提案。反映成功で破棄。
  • 反映：確認モーダルに「差分のある品目一覧（±0と未入力は載せない）」→ 確定で POST /rpc/pharmacy_apply_stocktake（入力済みの全行を送る。±0の行も棚卸実績として stocktakes に記録される）。
  • 反映後：マスタ再読込・在庫画面の数値ロール・トースト「88品目を棚卸し、差分2件を反映しました」。
  • モバイル（1品モード）：QRスキャン→その薬の実地数を大きなテンキーで入力→「次の薬へ」。内部的には同じ draft に積み、反映は同じRPC。

8.2 受け入れ条件

  1. 実地数を2品目だけ入れて反映すると、①stocktakes に2行 ②差分のあった品目だけ adjust トランザクション ③medicines.current_stock が実地数どおり、になる。未入力品目は一切変化しない。
  2. 差分0の品目は stocktakes に記録されるが transactions は増えない。
  3. 反映前にリロードしても下書きが復元される。
  4. 同じ内容で反映を2回実行できない（成功後はボタンが初期化され、draftが消えている）。
  5. 反映後の在庫一覧・v0.7側の在庫表示も同じ数値になる（DB共有の確認）。

SECTION 13GAS連携の扱い

v0.7でのGAS用途v0.8での扱い理由
出庫時の処方履歴記録（recordPrescription→夜間外来DB）維持fire-and-forget で送信カルテ運用・夜間外来KPIが参照している可能性があり、勝手に切れない（要確認事項①）
batch（stockIn/stockOut/stockAdjust→在庫サマリーシート）廃止（要確認）Supabaseが唯一の正（v0.6で確立）。シート側の同名重複・区切り行問題の温床。凍結を明示したい
addMedicine（薬品マスタのGAS登録）廃止（要確認）二重登録の解消（課題1）。GASシートは今後参照しない
getStock（Supabase不通時のフォールバック表示）廃止（要確認）localStorageキャッシュのみで代替「DBに繋がらない時は前回キャッシュ＋読み取り専用」の方が安全（GASサマリーは信頼できないと判明済み）
カルテ薬品マスタ突合（KARTE_API_URL・読み取り）維持1日1回・今日の状態に表示未登録薬の取りこぼし防止に有効（実績あり）
GAS_TOKEN はページ内に露出する（v0.7と同条件）。v0.8で新たな秘密情報を追加しないこと。
